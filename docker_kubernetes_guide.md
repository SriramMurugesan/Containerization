# Comprehensive Guide to Docker & Kubernetes

This guide covers Docker basics for Linux and macOS, common interview questions, three practical containerization scenarios (FastAPI, React, and both combined), and a Kubernetes "Hello World" deployment for a React app.

---

## 1. Using Docker: Linux vs. macOS

### Understanding Docker
Docker uses OS-level virtualization to deliver software in packages called containers. Containers are isolated from one another and bundle their own software, libraries, and configuration files.

### Docker on Linux
Docker natively shares the host's Linux kernel. This means containers run with virtually no overhead, directly hitting the host OS kernel. Processes in a Docker container are just standard Linux processes wrapped in cgroups and namespaces.

### Docker on Mac
macOS does not natively have a Linux kernel. When you install Docker Desktop on a Mac, it actually spins up a lightweight Linux virtual machine (using HyperKit or the Apple Virtualization Framework). Docker containers are then run *inside* this Linux VM. This adds a slight overhead compared to native Linux, but Docker Desktop hides this complexity, making the developer experience seamless. File sharing between the Mac host and the Linux VM is also handled automatically.

## 2. Top Docker Interview Questions

1. **What is the difference between a Docker Image and a Docker Container?**
   * **Image:** A read-only template containing instructions for creating a container. It's the built application and its environment.
   * **Container:** A runnable instance of an image. It has its own state, filesystem, and network interface.

2. **What is Docker Compose?**
   Docker Compose is a tool for defining and running multi-container Docker applications. You use a YAML file (`docker-compose.yml` or `compose.yaml`) to configure your application's services, networks, and volumes, allowing you to start them all with a single command (`docker compose up`).

3. **Explain Docker Volumes.**
   Containers are ephemeral; when they are deleted, all data inside them is lost. Volumes are the preferred mechanism for persisting data generated by and used by Docker containers. They are stored outside the container's lifecycle on the host OS.

4. **What is a multi-stage build?**
   A multi-stage build uses multiple `FROM` statements in a single Dockerfile. You can selectively copy artifacts from one stage to another, leaving behind everything you don't want in the final image. This drastically reduces the final image size (e.g., building a Go or Node.js app in one stage, and copying only the compiled binaries/static files to an alpine/nginx production image).

5. **How does Docker handle networking?**
   Docker creates an isolated internal network for containers. By default, containers on the same network can communicate with each other using their container names as hostnames. Ports can be mapped to the host (`-p 8080:80`) to allow external access.

## Part 1: FastAPI Backend with Docker

Let's create a "Hello World" FastAPI backend.

### Project Structure (FastAPI)
```text
fastapi-docker/
├── main.py
├── requirements.txt
└── Dockerfile
```

### 1. `main.py`
```python
from fastapi import FastAPI

app = FastAPI()

@app.get("/")
def read_root():
    return {"message": "Hello from FastAPI Backend!"}

@app.get("/api/data")
def get_data():
    return {"data": "This is data from the database or backend logic."}
```

### 2. `requirements.txt`
```text
fastapi>=0.100.0
uvicorn>=0.23.0
```

### 3. `Dockerfile`
```dockerfile
# Use official Python lightweight image
FROM python:3.11-slim

# Set the working directory
WORKDIR /app

# Copy requirements and install
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy the rest of the application code
COPY . .

# Expose port
EXPOSE 8000

# Run the FastAPI app using Uvicorn
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**How to run it:**
```bash
cd fastapi-docker
docker build -t my-fastapi-app .
docker run -d -p 8000:8000 my-fastapi-app
# Visit http://localhost:8000/
```

## Part 2: React Frontend with Docker

We will use a multi-stage Docker build to compile the React app and then serve the static files using Nginx.

### Project Structure (React)
```text
react-docker/
├── src/
│   ├── App.js
│   └── index.js
├── package.json
└── Dockerfile
```

### `Dockerfile` (Multi-stage)
```dockerfile
# Stage 1: Build the React Application
FROM node:22-alpine as build

WORKDIR /app

# Install dependencies
COPY package*.json ./
RUN npm install

# Copy source code and build
COPY . .
RUN npm run build

# Stage 2: Serve the application with Nginx
FROM nginx:alpine

# Copy the built output from Stage 1 to Nginx's html folder
COPY --from=build /app/build /usr/share/nginx/html

# Expose Nginx default port
EXPOSE 80

# Start Nginx
CMD ["nginx", "-g", "daemon off;"]
```

**How to run it:**
```bash
cd react-docker
docker build -t my-react-app .
docker run -d -p 3000:80 my-react-app
# Visit http://localhost:3000/
```

## Part 3: Combined FastAPI and React Setup (Docker Compose)

In a real scenario, you want your React frontend and FastAPI backend running together.

### Project Structure (Combined)
```text
fullstack-app/
├── frontend/             # Your React code + Dockerfile
├── backend/              # Your FastAPI code + Dockerfile
└── compose.yaml          # The Docker Compose file connecting them
```

### `compose.yaml`
```yaml
version: '3.8'

services:
  # The FastAPI Backend
  api:
    build: ./backend
    ports:
      - "8000:8000"
    environment:
      - ENV=development
  
  # The React Frontend
  web:
    build: ./frontend
    ports:
      - "3000:80"
    depends_on:
      - api
```

### Making Frontend talk to Backend
In your React code (`src/App.js`), when you make a fetch request, you will use `http://localhost:8000/` if accessing it from your browser, or if using an internal Nginx proxy config, route `/api` to the `api:8000` service.

For simple local development, React fetch calls would look like:
```javascript
fetch("http://localhost:8000/api/data")
  .then(res => res.json())
  .then(data => console.log(data));
```

**How to run the combined stack:**
```bash
cd fullstack-app
docker compose up -d --build
```
This single command builds both images, creates a default network so they can communicate, and starts the containers mapping the correct ports to your host.

## Kubernetes: Hello World for React

Kubernetes (K8s) is an orchestrator. To run our React Docker image on K8s, we need two main concepts:
1. **Deployment**: Ensures that a specified number of application replicas (pods) are running.
2. **Service**: Exposes our deployment to the network (so we can reach it from our browser).

### 1. `react-deployment.yaml`
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: react-app-deployment
  labels:
    app: react-frontend
spec:
  replicas: 2 # Run 2 instances of our React app for high availability
  selector:
    matchLabels:
      app: react-frontend
  template:
    metadata:
      labels:
        app: react-frontend
    spec:
      containers:
      - name: react-container
        image: my-react-app:latest  # The image we built in Part 2
        imagePullPolicy: Never      # Use local image (for minikube/Docker Desktop testing)
        ports:
        - containerPort: 80         # Nginx runs on port 80 inside the container
```

### 2. `react-service.yaml`
```yaml
apiVersion: v1
kind: Service
metadata:
  name: react-app-service
spec:
  type: NodePort  # Allows access from outside the cluster
  selector:
    app: react-frontend # This links the Service to our Deployment pods
  ports:
    - protocol: TCP
      port: 80          # Port inside K8s network
      targetPort: 80    # Port the container listens on
      nodePort: 30005   # Port you use in your browser (localhost:30005)
```

**How to deploy to Kubernetes (assuming Minikube or Docker Desktop K8s is running):**
```bash
kubectl apply -f react-deployment.yaml
kubectl apply -f react-service.yaml

# Check if pods are running
kubectl get pods

# Check if service is up
kubectl get services

# Visit the app
# Depending on your K8s setup, it might be available at http://localhost:30005 
# Or if using minikube, run `minikube service react-app-service` to get the URL.
```
